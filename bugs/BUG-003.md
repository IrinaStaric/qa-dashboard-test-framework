# BUG-003 – Protected pages briefly render before redirecting unauthenticated users

## Summary
When an unauthenticated user attempts to access protected routes directly via URL, the application briefly renders the application loading state before redirecting to the Sign In page. This creates a visible flicker suggesting partial initialization of protected areas prior to authentication validation.

## Environment
- Affected routes:
  - /assets
  - /devices
  - /vulnerabilities
  - /managementAssets
  - /managementDevices
  - /managementVulnerabilities
  - /assetDashboard
  - /devicesDashboard
  - /vulnerabilitiesDashboard
- Browser: Chrome
- OS: macOS
- App version: local environment (http://localhost:5480)

## Steps to Reproduce
1. Log in as an admin user.
2. Sign out.
3. Manually change the URL from `/auth` to any protected route (e.g. `/assets`).
4. Observe the page behavior during navigation.

## Actual Result
- A loading screen (“Loading app data…”) is displayed for 1–2 seconds.
- The application then redirects to the Sign In page.
- During this time, the application appears to initialize protected sections before authentication is fully validated.

## Expected Result
- Unauthenticated users should be immediately redirected to the Sign In page.
- No application initialization or loading state related to protected content should be visible before authentication is confirmed.

## Security Consideration
Although no protected API responses with successful status codes were observed during verification, the current behavior may create a perception of partial access to protected areas and increases the risk of unintended data exposure if future changes introduce delayed authorization checks.

## Impact
- Potential security concern due to premature rendering of protected application state.
- User experience degradation caused by visible flickering during redirects.
- Authentication guard appears to be applied after initial render rather than before route resolution.
